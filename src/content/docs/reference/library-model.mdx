AnyPS5 executes converted PlayStation 5 binaries against reimplemented dynamic libraries known as PRX libraries. Rather than emulating hardware registers or operating system kernel traps, AnyPS5 converts calls to system libraries into dynamic function calls resolved by the host operating system dynamic linker.

## System PRX libraries

On the PlayStation 5, system software is organized into dynamic shared libraries called PRX modules (PlayStation Relocatable Executable). These modules expose symbols not by plain text names alone, but by numeric or alphanumeric identifiers known as NIDs (Numeric Identifiers).

AnyPS5 builds native dynamic libraries (Linux `.so` or Windows `.dll`, installed with a `.prx` extension in `libs/`) that export these symbols. When a converted ELF or PE executable starts, the host dynamic linker binds its import table directly to the functions exported by these libraries.

## The NID algorithm

A NID is an 11-character identifier generated by hashing the original C/C++ symbol name with a cryptographic salt. AnyPS5 computes NIDs using the following exact algorithm:

1. **Input concatenation**: Take the plain symbol name (for example, `sceAudioOutOpen`) as UTF-8 bytes and concatenate a 16-byte proprietary salt:
   ```
   0x51, 0x8D, 0x64, 0xA6, 0x35, 0xDE, 0xD8, 0xC1,
   0xE6, 0xB0, 0x39, 0xB1, 0xC3, 0xE5, 0x52, 0x30
   ```
2. **SHA-1 digest**: Compute the 20-byte SHA-1 hash over the combined buffer.
3. **Byte reversal**: Take the first 8 bytes of the resulting digest and reverse their order, treating them as a little-endian 64-bit unsigned integer.
4. **Base64 encoding**: Encode the 64 bits into an 11-character string using the URL-safe Base64 character set:
   ```
   ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+-
   ```

The resulting 11-character string represents the exported NID symbol. When compiling PRX libraries, tool scripts patch export tables so symbols match the NIDs expected by the executable GOT/PLT entries.

## Function states

Every export declared across AnyPS5 system libraries exists in one of three distinct states:

### Implemented

The function contains active logic that translates PlayStation 5 parameters to host platform operations. Examples include:

- Translating memory allocation calls to host `mmap` or `VirtualAlloc`.
- Submitting graphics packets to Vulkan command buffers.
- Routing audio sample buffers to SDL audio output queues.
- Reading game controller inputs from SDL gamepads.

### Inert (silent stub)

An inert function is a deliberate stub that returns a valid success code (such as `0` or `SCE_OK`) without executing real system actions. Inert stubs are strictly restricted:

- They are permitted only when missing implementation would cause a title to fail during startup or non-essential background tasks.
- They must only affect user interface elements, telemetry reporting, or optional system services (such as trophy synchronization or analytics).
- Every inert stub must be cataloged under the Silent stubs section of the corresponding library technical debt file in `docs/dev/debt/`.

### Stub (unimplemented)

When a function is declared but lacks host implementation logic, it calls:

```cpp
NotImplemented_nid_no_patch(__func__);
```

This helper prints an informative error message to standard error indicating the library name and function symbol, then throws `std::runtime_error`. The runtime terminates immediately, ensuring missing logic is never masked by invalid state.

## Calling convention bridging

PlayStation 5 binaries use the standard System V AMD64 ABI:

- Integer and pointer arguments are passed in registers: `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`.
- Floating-point arguments are passed in registers: `xmm0` through `xmm7`.
- Return values are returned in `rax` or `xmm0`.
- The caller cleans up stack space.

### Host platform handling

On Linux hosts, the native operating system ABI matches the System V AMD64 ABI. Function calls from the converted ELF into `.prx` libraries execute without register translation overhead.

On Windows hosts, the native ABI is the Microsoft x64 calling convention (`rcx`, `rdx`, `r8`, `r9`). To allow converted PE executables to call PRX functions compiled for Windows, AnyPS5 decorates all PRX exports with the `APS5_VABI` macro:

```cpp
#if defined(_WIN32)
#define APS5_VABI __attribute__((sysv_abi))
#else
#define APS5_VABI
#endif
```

The host compiler generates code that saves and restores registers according to the System V AMD64 ABI specification, enabling direct interoperation on Windows without intermediate wrapper thunks.

## Symbol export naming conventions

Symbols defined within PRX source files adhere to specific naming conventions recognized by build automation:

- Standard exports: Named with their canonical API names (such as `sceKernelAllocateDirectMemory`). The post-build NID patcher replaces these with their corresponding 11-character NID hashes.
- Internal helper symbols: Appended with `_nid_no_patch` or `_nid_no_patch_cut` to instruct the NID patcher to preserve the original symbol name for internal linking.
